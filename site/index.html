Easy Verifier

An offline, rule-based repository verifier, available as an MCP server and a CLI. It rates a repository, or a change, from declared rules over measured facts, and says so when it cannot rate something.

What it is

Easy Verifier gathers evidence about a repository (file excerpts, citations, and lists of what it looked for and did not find) and computes inspectable ratings from declared rules. A calling agent can optionally submit its own findings for a separate assessment.

  • No inferred verdict. Ratings are deterministic arithmetic over cited metrics.
  • No guessing. A source it did not find is reported as missing; a rating without enough evidence is withheld.
  • Read-only and local. It never executes the repository's code and makes no outbound network request.

Terms used below: a dimension is one independently rated aspect (for example security); an evaluation area is one of 32 cited review topics a rule can measure; an abstention is "no number, with a reason code".

Run it

Three steps with Docker: pull the image, run it, register it. Nothing is built.

1. Pull

docker pull temvar/easy-verifier-mcp:0.1.0

2. Run

Replace both /home/you/code with the absolute parent directory of the repositories you want to score.

mkdir -p ~/.easy-verifier-reports ~/.easy-verifier-sot
sudo chown 10001:10001 ~/.easy-verifier-reports ~/.easy-verifier-sot

docker run -d --name easy-verifier --restart unless-stopped --init \
  --read-only --network host --cap-drop ALL \
  --security-opt no-new-privileges:true \
  --tmpfs /tmp:rw,noexec,nosuid,nodev,size=16m \
  -e EASY_VERIFIER_REPORTS_DIR=$HOME/.easy-verifier-reports \
  -e EASY_VERIFIER_SOT=/sot \
  -v /home/you/code:/home/you/code:ro \
  -v $HOME/.easy-verifier-reports:$HOME/.easy-verifier-reports \
  -v $HOME/.easy-verifier-sot:/sot \
  temvar/easy-verifier-mcp:0.1.0 --transport streamable-http

3. Register

claude mcp add --transport http easy-verifier http://127.0.0.1:8766/mcp

Then ask your agent to score a repository, passing its absolute path as repo.

Other ways to run it

Build from source (Compose)

From a clone of the repository, build the same image yourself and start it with the absolute parent directory of the repositories you want to score:

docker compose build scorer
mkdir -p ~/.easy-verifier-reports && sudo chown 10001:10001 ~/.easy-verifier-reports
EASY_VERIFIER_WORKSPACE=/home/you/code docker compose up -d scorer

Without a container (stdio)

Install the package into a Python 3.11+ environment and register the stdio server:

python -m pip install .
claude mcp add easy-verifier -- easy-verifier-mcp

CLI

python -m easy_verifier.adapters.cli score --repo . --scope project

Full guides are in the repository: README.md, docs/DOCKER_MCP_GUIDE.md and docs/LOCAL_MCP_GUIDE.md.

How scoring works

One repository goes in at the top. Each dimension follows the same path: it ends either in a number from 0 to 100 or in an abstention, never a guess.

A worked example

Taken from the sample scorecard below: three of its rated dimensions and one abstention.

DimensionOutcome
architecturerated 100
test-strategyrated 75
securityrated 50
supply-chainabstains, too little measured: insufficient_measured_weight

The overall is 47: the mean of all 10 rated dimensions in that run. The abstained dimensions are left out, not counted as zero.

The rules in detail

  • Each dimension has declared rules over measured metrics. A rule compares one metric with a threshold; a met rule earns its weight and an unmet rule earns zero. The weights of the rules that apply at one scope add up to 100; solution-fit has no static rule.
  • Each rule cites its metric and its threshold separately. A threshold tagged project-default means the standard names the measure but publishes no number.
  • A coverage floor guards every dimension: if too little of the evidence it needs was found, it abstains with a reason code rather than showing a number. A metric that cannot be measured is left out of both the earned and the total weight.
  • The overall is the mean of the dimensions that could be rated, and the scorecard names which dimensions contributed and which abstained.
  • The improvement plan lists unmet rules ordered by their declared gain, recomputed from the same arithmetic, so fixing the top item is worth exactly the points shown.
  • The engine makes no model call and no network request. The same repository state gives the same score.
  • change-risk is rated only at changes or worktree scope, and is not averaged into the overall.
